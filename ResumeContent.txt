B.2 src/external-repos/Ztp (Zero-Touch Provisioning subsystem)
What it is.
The subsystem that lets a factory-reset G30/G32/G34c/G42 NE self-configure. When the NE boots without any config, ZTP negotiates DHCP on the management port, discovers a provisioning server via DHCP options 43 / 66 / 67, downloads a target software image and a config file, applies them, and reboots into the customer-managed state. It also implements ZTP-over-OSC (Optical Supervisory Channel) so an SNE (Small-form Network Element) can be ZTP'd via a relay node when it has no direct management connectivity.

Design highlights.

Ztp/cpp/DbfAgent/ZtpAgent.cpp — the main C++ state machine driven by DBF (Database Framework) callbacks.
Ztp/ztpmgr.py — Python orchestrator that runs the OS-level operations (dhclient, systemctl, ip vrf exec).
Ztp/Dhcp/ — DHCP client integration.
grpc/ — zgrpcclient for SNE-over-OSC provisioning: the SNE runs a gRPC client that talks to the relay NE over OSC to fetch its config.
service/ + Ztp/service/ — systemd unit files.
test/ut/cpp/ — unit tests (recently massively expanded).
ai_docs/ — repo-specific AI context (OTS line-alignment feature docs, ZTP_CONTEXT.md, OSPF auto-assignment design).
Uses ip vrf exec MGMT/CTRL heavily — many operations are VRF-scoped.

B.3 src/external-repos/filetransferservice (FTS / ftsmgr)
What it is.
The chassis file-transfer daemon. Its single binary ftsmgr runs on every card that needs to move files (image, database, config, PM files, dbgxfr archives). It exposes an RPC surface (RpcHandler) that other subsystems (ZTP, SWM, dbf, PM collectors) invoke to put / get files, then does the actual transfer via libcurl for SCP / SFTP / FTP / HTTP / HTTPS. It maintains transfer state in the DB (ioa_network_element__transfer_status) via DBI so external observers (CLI, NBI, TNMS) can monitor progress in real time.

Design highlights.

src/FTSManager.cpp (3060 lines) — the central class; owns uploadToRemoteServer, downloadFromRemoteServer, setTransferStatus, and the throttler wiring.
include/FTS.h (1028 lines) — the public interface + interfaceBasedPut/Get legacy shell-curl fallback path.
include/RpcHandler.h — external RPC surface + setLastProgressValues / getLastTotalBytes / getLastBytesTransferred.
util/ProgressIndicatorThrottle.h — the 5%/5s/slow-path coalescer you introduced.
util/FtsThrottleConfig.h — DBI-tunable throttle configuration.
listeners/ — DBF change listeners.
aidlc-docs/, docs/, DOCS/ARCHITECTURE.md, DOCS/CONTEXT_NEW.md — the AI-workflow-aware documentation stack.
Runs as ftsmgr.service systemd unit (ftsmgr.service, ftsmgr_start.sh).
Supports --interface binding (LO-MGMT, MGMT, arbitrary VRF-scoped interfaces) — critical for multi-VRF chassis where the transfer must egress a specific interface.
Two curl paths: in-process libcurl (Service::put / Service::get — full callback fidelity) and shell curl (interfaceBasedPut/Get — used when VRF L3-MDEV isn't available; no progress callbacks).

Part E — Cross-cutting patterns / lessons
These are the recurring engineering lessons visible across the JIRAs:

Small surgical diffs for customer escalations. Every Tier-4/customer JIRA (GX-223031, GX-243105, GX-281131, GX-282836) landed with < 30 LOC of code change plus supporting logging. You explicitly rejected redesigns under time pressure.
Documentation as load-bearing infrastructure. GX-261604 (FTS AI docs) enabled GX-265733 + GX-272386. GX-268026 UT docs enabled GX-273852. Docs are inputs to tools, not just for humans.
Logging discipline is a product surface, not polish. Five JIRAs are essentially "get the right log at the right level" work: GX-243105 nginx, GX-274279 HTTP warning, GX-269439 CFG_MGR_RESTART soak, GX-288080 FTS logs, GX-282815 zgrpc cleanup logs.
Rate limiting shows up everywhere. The same underlying pattern (coalesce high-frequency producer, gate at producer not consumer) appears in FTS throttler, CFG_MGR_RESTART soak, and EQM callback narrowing. Same lesson, three domains.
Simulation parity is a force multiplier. Once ZTP-in-DSIM (GX-186925/210345/215042/217540) landed, iteration on subsequent ZTP JIRAs (GX-274279, 269439, 282836, 282815) sped up dramatically. Every hour spent on DSIM saved days on later customer fixes.
AI-DLC = context + boundary contracts + review, not "run a prompt". The heavy commit counts on GX-268026 (rename, consolidate, fix link errors, remove seg-fault tests) show what the loop actually costs — the AI produced the volume, but you produced the shape.
Multi-round reviews are the norm on customer hot paths. GX-272386 (~64% of commits were rework) and GX-274279 (13 commits to converge on a warning message) show that landing customer-critical code takes multiple review rounds by design.
